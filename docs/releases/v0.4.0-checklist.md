## Cut the release

1. Require all three CI jobs to pass on the versioned candidate. If the preparation PR is merged, use the resulting main commit and its own successful build; do not tag a merge commit while publishing a different commit’s assets.
2. Download `release-v0.4.0-x86_64` from that successful run. Check `BUILD.txt`: version 0.4.0, expected commit and tree, architecture x86_64, correct workflow run/attempt.
3. Run `sha256sum --check SHA256SUMS` with the complete bundle present. Verify package metadata says `omarchy-retro-arcade`, `0.4.0-1`, `x86_64`; retain corresponding source and pinned engine/network inputs. Do not substitute the separately uploaded debug-symbol package for the player package.
4. Record candidate CI/asset results in the release description. Remove the candidate-status sentences from the public release copy only when publication happens; the bundled build-time notes remain unchanged and checksummed. Carry the live-testing limits forward honestly.
5. Create tag `v0.4.0` at the exact `BUILD.txt` commit and publish the matching five bundle files: player package, corresponding-source archive, `BUILD.txt`, `RELEASE-NOTES.md`, `SHA256SUMS`. Never move an existing release tag.
6. Verify the published asset digests and version, then update README download/install references from v0.3.0 to v0.4.0 and remove the preparation notice.

No tag, public release or package-repository promotion is created by this preparation. Package-repository submission is a separate operation.
